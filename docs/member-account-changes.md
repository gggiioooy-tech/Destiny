# Nickname changes and persistent login

Members can change their own game nickname from the sidebar. Administrators can change a member's nickname from the nickname column in Member Management. Both use the same authenticated transaction; direct browser updates of `profiles.game_nickname` are revoked.

The transaction reserves the previous/new normalized names within the member's administrator-assigned guilds and links them to the stable profile ID. It rejects another member's current or reserved former name in the same guild. Different guilds can have the same nickname. Known aliases are resolved to the current profile nickname in both sides of historical battle payloads and in later imports; opponent-side resolution requires that opponent's guild to be known. The generated member nickname and search indexes update through existing triggers, keeping occurrence times, source keys and results unchanged. No date cutoff is imposed. The UI clears its history cache and reloads account/page data after a successful change.

Aliases are private, RLS-enabled with no client table grants. The exposed RPC is security invoker and delegates to an internal function that checks the live session, approval and administrator authorization for editing another member. Nickname edits do not alter roles, guild membership or passwords. Guild/name links reflect the site's existing identification scheme; they do not claim to recover an unavailable game account UID or an unknown historical opponent guild.

The separate Login Keep checkbox switches the Supabase session adapter between temporary session storage and durable local storage. It stores the SDK session, never a password. Explicit logout removes both session copies and the keep-login preference. Browser storage failures produce an error rather than silently claiming persistence. Existing server session revocation and approval checks remain in force.

Validation: `scripts/verify-member-nickname.sql` uses synthetic profiles/auth sessions/observations in a rolled-back transaction. It checks self/admin edits under the authenticated database role, repeated renames, later imports of the original name, unchanged attack/defense win counts, mirror records, cross-guild collisions, empty/duplicate names and unauthorized calls. No real member profile is modified by these tests. Six storage tests include the actual Supabase SDK with synthetic tokens and a mock Auth endpoint for save/reopen/signout. `scripts/verify-account-ui.mjs` checks the login controls and nickname forms by SSR; this is not interactive browser QA. The full JavaScript suite passes 454 tests; guild-filter regressions and production build pass. The production dependency audit is clean; six pre-existing moderate development-tool findings remain.
