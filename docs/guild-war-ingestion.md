# 길드전 기록 수신 계약

대상: 15월 Supabase 프로젝트 `kqygrszkbuzxmmfndhye`.
PC 자동 수집기 연결은 아직 구현되지 않았다. 이번 변경은 길드 탭, 집계/조회 화면 및 인증된 업로드 RPC를 제공한다. 실험용 캡처 기록은 업로드하지 않았다.

## 길드와 권한

- `guild_war_tabs`에 철폐·서리를 초기 등록한다.
- 관리자는 `add_guild_war_tab(p_name)`으로 회원 메모의 쉼표 구분 길드명 중 하나를 추가한다. 일반 회원/게스트는 추가할 수 없다.
- 업로드는 유효한 Supabase 로그인 세션이 있는 승인된 회원/관리자만 가능하다. 소유자만 수정 가능한 `profiles.memo`를 서버가 읽는다. 클라이언트의 길드 이름/작성자 ID는 신뢰하지 않는다.
- 메모에 서로 다른 이름이 정확히 하나면 그 길드에 귀속된다. 탭 미등록 길드 기록은 저장하되 조회 대상에서 제외한다. 탭을 추가하면 이전 보류 기록도 보인다.
- 메모가 비었거나 여러 길드가 있으면 `guild_name=null`로 보류한다. 나중에 메모를 고쳐도 과거의 모호한 기록은 자동 재분류하지 않는다.
- 현재 두 탭은 승인 회원/관리자 공통 열람이며, 게스트와 비로그인은 조회할 수 없다.

## 업로드

`supabase.rpc('submit_guild_war_observation', {p_kind, p_source_key, p_occurred_at, p_payload})`

- `p_kind`: `battle` 또는 `defense_snapshot`.
- `p_source_key`: 같은 전투를 여러 수집기가 동일하게 식별하도록 전투 시각, 공격자/방어자 ID, 자리, 전쟁 식별자에서 만든 안정적인 해시. 스냅샷은 전쟁 ID/수집시각/내용 해시를 사용한다. 최대 200자.
- `p_occurred_at`: ISO 시각. 10분을 초과하는 미래 시각은 거부한다.
- `p_payload`: 최대 512KiB JSON 객체. 토큰, 계정 로그인 정보, 패킷 원문, 리플레이 URL을 넣지 않는다.
- 응답 `status`: `recorded`, `held`, `duplicate`. `guild`는 서버가 해석한 이름 또는 null.
- 같은 회원·종류·키의 재전송은 덮어쓰지 않는다. 전투 기록은 스킬 보강 등 정규화를 마친 뒤 업로드한다. 현재 API에 수정/삭제 기능은 없다.
- 클라이언트가 보내는 사실관계 자체의 진위 검증은 별도 수집기 과제다. 로그인/길드 권한 검증과 게임 데이터의 진위 검증은 구분한다.

전투 payload 예시:
```json
{"castle":"외성1","attackerWon":true,"attacker":{"nickname":"공격자","heroes":["루디","스파이크","클레미스"],"pet":"연지","skills":[{"hero":"루디","skill":"아래"}]},"defender":{"nickname":"방어자","heroes":["델론즈","아일린","젠이츠"],"pet":"펫 이름","skills":[]}}
```

방어 스냅샷 payload 예시:
```json
{"total":90,"defenses":[{"castle":"외성1","nickname":"상대","heroes":["선란","탄지로","하연"],"pet":"연지"}]}
```

스냅샷은 해당 수집기가 확인한 전체 누적 목록을 전송한다. `total`을 모르면 생략한다. 전쟁 ID를 포함한 최신 스냅샷으로 관리해야 하며, 실제 전쟁일의 전체 수신/부분 수신 범위는 아직 미검증이다.
화면은 최신 스냅샷 하나와 최근 200개 전투 관측을 읽으며, 15초마다 표시 중인 탭을 갱신한다. 영웅 순서가 달라도 성/영웅 조합/펫이 같으면 합산한다. 추천 카운터는 기존 사이트의 상대 영웅 조합으로 매칭하며 상대 펫 호환성을 보장하지 않는다.
